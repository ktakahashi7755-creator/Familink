# 要件定義：招待コードの失効 / ローテーション（家族共有の安心）

> 優先度 **A**（App Store 公開前に入れたい安心機能）。
> 本書は要件整理＋設計選択肢の提示まで。**RLS / データモデル変更を伴う実装は §14.3 によりオーナー承認後に着手**する。
> 関連：`docs/supabase-backend-plan.md`（§4.3, §5）／`docs/supabase-setup-sql.sql`（現行 RLS）／`docs/family-sharing-fix-2026-06-07.md`

最終更新：2026-06-08

---

## 0. なぜ必要か（課題）

現状、招待コードは **trust-based で失効手段がない**：

- コードを知っている人は、退会させない限り**無期限で家族の予定・家計・体調・写真を閲覧**できる。
- コードが漏れた／元家族・元交際相手などに渡った場合、**取り消す方法がない**。
- 高プライバシー情報（子ども・体調・家計）を扱う以上、App Store 審査・家族の信頼の観点で弱点（§13）。

---

## 1. 現行実装と当初設計の乖離（設計の核心）

| 項目 | 当初設計（backend-plan §4.3/§5） | 実装済み（familink.html） |
|---|---|---|
| データモデル | `families` + `family_members` + `family_data` | 単一 `fl_family_data` のみ |
| コードと家族の関係 | `families.invite_code`（コードと family_id を**分離**） | **コード＝family_id**。各行の `family_id` 列に直接保存 |
| 参加 | RPC `join_family(code)` | クライアントが自分の行の `family_id` をコードに更新 |
| 再発行 | 「漏洩時はオーナーが再発行できる設計にする」と明記 | **未実装・構造的に困難** |

**核心**：実装では「コード＝家族の主キー」のため、コードを変えると**全メンバーの行を新コードへ移行**しないと家族が割れる。当初設計の `families` テーブルがあれば「`invite_code` だけ差し替え」で済む。ここが失効実装の分岐点。

---

## 2. ユーザーストーリー

- **親（オーナー）として**：コードが漏れたかもと思ったら、**今のコードを無効化して新しいコードに切り替え**たい。信頼できる家族だけが引き続き見られる状態にしたい。
- **親（メンバー）として**：オーナーがコードを切り替えても、**自分は再入力なしで家族の共有を続け**たい（できれば）。
- **家族全体として**：切り替え後、**古いコードを持つ第三者からは新しいデータが見えなくなる**こと。

---

## 3. 実装オプション（推奨度順）

### Option C ＝ 近未来・無バックエンド「実質失効」（推奨・低リスク）
既存機能（`leaveFamilyGroup` + `openMyInviteModal`）の組み合わせ＋UI 導線追加のみ。スキーマ変更なし。

- 流れ：オーナーが「コードを作り直す」→ 新コード発行 → 信頼できる家族に新コードを再共有 → 各自が新コードで参加し直す。
- 効果：全員が新コードへ移れば、**古いコードの家族には漏洩者だけが残り、新しいデータは見えない**（実質的な失効）。
- 限界：メンバー全員の**再入力が必要**。移行が完了するまで一時的に二重状態。完全な強制失効ではない。
- 実装：設定の家族共有セクションに「コードを作り直す（再発行）」ボタン＋手順説明モーダルを追加。**§14.2 の自律範囲で実装可能**（UI＋既存関数の組合せ）。

### Option B ＝ 本命・`families` テーブル導入（要オーナー承認）
当初設計（backend-plan §4.3）へ寄せる。`fl_family_data` を**安定 uuid の family_id**で keying し、コードは `families.invite_code` に分離。

- ローテーション＝`families.invite_code` を更新するだけ。**メンバーは再入力不要**、漏洩コードは即無効。
- 必要作業：新テーブル＋RLS 全面改訂＋RPC（`create_family`/`join_family`/`rotate_invite_code`）＋既存 `fl_family_data` の移行。
- リスク：**RLS / データ構造変更（§14.3 停止対象）**。Supabase SQL 再適用必須。移行ミスは家族共有停止に直結。
- 位置づけ：**正しい最終形**だが中規模。要件・移行計画・テストを固めてからオーナー承認のうえ着手。

### Option A ＝ クライアントのみで強制ローテーション（非推奨）
Realtime で「新コードへ移行」を全端末に通知し各自の行を書き換える案。オフライン端末が取り残され家族が割れるため**不採用**。

> **推奨**：まず **Option C** を実装して「実質失効」を提供（公開前の安心を確保）。本命の **Option B** は別途承認を得てロードマップ化。

## 4. 受け入れ条件（Option C・近未来分）

- **AC1**：設定 → 家族共有に「コードを作り直す」導線がある。タップで二段階確認（§13.6）後、新コードを発行して表示する。
- **AC2**：作り直すと自分の `familyId` が新コードに変わり、クラウドへ反映される（ログイン時）。
- **AC3**：作り直し時に「**信頼できる家族に新しいコードを伝え、各自で参加し直してもらう必要がある**」旨を明示する（誤解防止）。
- **AC4**：未ログイン／CDN 未接続時は、その状態に応じた注意文を出す（既存の出し分けと一貫）。
- **AC5**：作り直してもこの端末のデータ（`familink_v3`）は消えない。
- **AC6**：iPhone SE 幅で説明文・ボタンが崩れない。タップ領域 44px 以上。

## 5. 画面仕様（Option C）

| 項目 | 内容 |
|---|---|
| 入口 | 設定 → 家族共有セクションに「コードを作り直す（再発行）」ボタン（控えめ・破壊的でない色） |
| 確認 | `showConfirm` で「古いコードは無効化されます。信頼できる家族に新しいコードを共有し直してください」 |
| 実行 | `_setFamilyId(_generateFamilyId())` → ログイン時 `_pushToSupabase()` → 新コードを `m-my-invite` で表示 |
| 表示 | 新コード＋「家族に新コードを伝えてください」＋再共有手順 |
| 遷移 | 設定へ戻る／そのまま共有モーダル |

## 6. データ要件

- **Option C**：既存 `S.familyId`/`familyIdOwner`/`familyIdSetByUser` のみ使用。**新規 LocalStorage キーなし／PERSIST 変更なし**。スキーマ変更なし。
- **Option B**：`families(id uuid, invite_code text unique, owner_id uuid, created_at)` 等を新設し、`fl_family_data.family_id` を uuid 化。**要 cto-architect 承認＋移行計画**（本書では確定しない）。

## 7. バリデーション / 文言（Hoku 口調）

- 確認文：「このコードを作り直すと、今のコードは使えなくなります。信頼できるご家族に新しいコードを伝えて、もう一度参加してもらってくださいね。」
- 完了トースト：「新しい家族コードを作りました。ご家族に共有してください😊」
- 未ログイン時：既存の「いまはこの端末だけに保存…」を踏襲。

## 8. テスト観点（QA 連携）

- 作り直し→新コードが旧と異なる／旧コードで別端末から新データが見えない（手動・多端末）。
- 作り直し後リロードで新コードが復元される。
- 未ログイン・オフライン・CDN 失敗時の注意文出し分け。
- 二段階確認のキャンセルで何も変わらない。

## 9. 未確定事項（オーナー判断）

1. **Option C を先行実装してよいか**（推奨・低リスク・UI のみ）。
2. **Option B（families テーブル）を中期ロードマップに載せるか**（本命・RLS/移行で要承認）。
3. コードの**有効期限**（例：90 日で自動ローテ提案）を入れるか。
4. 「最後に参加した端末一覧」を見せて**個別失効（kick）**まで踏み込むか（Option B 前提）。

## 1. プロダクトビジョン（北極星）

### 1.1 ビジョンステートメント

> **「家族みんなで子育てをチームにするアプリ」**

3児のパパ・ママ・祖父母を含む家族全員が、子育てをひとりに背負わせず**チームで回せる状態**を作る。
単なる予定共有アプリではなく、家族の生活導線に入り込む**家族オペレーションのハブ**を目指す。

### 1.2 解決する課題

| 課題 | 現状の痛み | Familink の解 |
|---|---|---|
| 子育て情報の属人化 | 予定・持ち物・体調がママ（または一人の親）の頭の中にだけある | 家族全員が同じデータを見る「家族の共有脳」 |
| 連絡の分散 | LINE・紙のプリント・口頭・冷蔵庫のメモに散らばる | 予定/タスク/ボード/書類を1アプリに集約 |
| 準備の抜け漏れ | 幼稚園・小学校の持ち物、行事準備の抜け | 準備リスト＋リマインド＋OCR取込で仕組み化 |
| 祖父母の疎外 | 送迎や預かりを頼みたいが情報が届かない | 招待リンク1つで祖父母も同じ情報圏に |
| 記録の断絶 | 体調・成長・家計の記録が続かない | 記録の敷居を下げ、Hoku が整理を支援 |

### 1.3 プロダクト原則（すべての判断の基準）

1. **家族の信頼を損なわない** — 高プライバシー情報（子ども・体調・家計・写真）を扱う自覚を持つ
2. **忙しい親が3秒で理解できる** — スマホ片手操作・迷わないUI
3. **無料で習慣化、有料で便利化** — 課金は価値の対価であり、囲い込みではない
4. **Hoku は道具ではなくガイド** — 押し付けず、そっと支える存在
5. **世界観の一貫性** — 落ち着いた配色・ラインアイコン・やさしい日本語（絵文字装飾禁止）

## 2. ターゲットとペルソナ

### 2.1 プライマリターゲット

- **共働き・子育て世帯**（子ども1〜3人、未就学児〜小学生）
- 家族単位で使う（1家族 = 1ユニット。個人アプリではない）
- サブターゲット: 送迎・預かりに関わる**祖父母世代**

### 2.2 代表ペルソナ

| ペルソナ | 属性 | 主要ニーズ | 主要利用機能 |
|---|---|---|---|
| ケンタ（父・38） | 3児のパパ・会社員・開発者本人がモデル | 家族の予定と持ち物を把握し、妻の負担を減らしたい | ホーム/カレンダー/タスク/Hoku |
| ミキ（母・36） | パート勤務・家族の情報ハブ役 | 頭の中の予定・準備を家族に「見える化」したい | カレンダー/準備リスト/家計/体調 |
| ヨシコ（祖母・65） | 近居・週2回送迎を担当 | 難しい操作なしで孫の予定だけ知りたい | ホーム/カレンダー（閲覧中心） |
| ハルト（長男・8） | 小学2年生 | 自分の持ち物・お手伝いを自分で確認したい | タスク/準備リスト（将来） |

### 2.3 利用シーン（ジョブ）

- 朝5分: 今日の家族の予定と持ち物を全員が確認する
- 園からのプリントを撮影 → OCR で予定表を一括取込
- 「土曜の運動会、おばあちゃんに送迎お願い」を予定＋担当者で共有
- 子どもの発熱を記録し、経過を家族と共有
- 月末に家計の記録を振り返る

## 3. 市場とポジショニング

### 3.1 市場観

- 国内の家族向けカレンダー共有市場は「TimeTree」等が先行するが、**予定共有単機能**が中心
- 子育て記録（ぴよログ等）・家計簿（マネーフォワード等）・連絡帳アプリは**縦割り**で家族全体を覆わない
- Familink は「**子育て家族のオペレーション全体**」を1つの世界観で覆う統合ポジションを取る

### 3.2 差別化の柱（真似されにくさ）

1. **統合体験**: 予定×タスク×持ち物×体調×家計×書類×ボードが1アプリ・1世界観で繋がる
2. **Hoku**: 家族データを理解した AI ガイドが、案内・取込・整理を代行する（機能でなく「関係性」の資産）
3. **家族単位の設計**: 個人アカウントの寄せ集めではなく、familyId を中心とした家族データモデル
4. **当事者性のブランド**: 「3児パパが作る家族向けアプリ」という実需発の物語
5. **軽さ**: 単一HTML・依存ゼロによる高速な改善サイクル（週次で磨ける開発体制）

### 3.3 モート（防御壁）の育て方

- 家族の生活データ蓄積 → スイッチングコスト（ただしエクスポートは誠実に提供）
- 家族招待によるネットワーク効果（1人の導入が家族全員の導入になる）
- Hoku の文脈理解の深化（利用が長いほど価値が上がる）

## 4. ビジネスモデル

### 4.1 収益モデル（正本: `docs/spec-v3/10-monetization.md`）

- **フリーミアム**: 無料で中核機能（予定/タスク/ボード/Hoku基本）を提供し習慣化
- **プレミアム 月額480円**（家族単位）: Stripe Checkout による実決済（Web/PWA）。権利はサーバ（`fl_entitlements`）が正本
- **30日全開放トライアル**で価値を先に体験させる
- 将来: 680/780/980円の上位プラン（家族レポート・AI強化・保存拡張）を段階導入

### 4.2 ユニットエコノミクスの考え方

- 課金単位は**家族**（個人課金より解約されにくく、LTV が家族継続に連動）
- 原価は Supabase・AI API・Stripe 手数料のみ（単一HTML構成によりインフラ費は極小）
- CAC はオーガニック中心（SNS・口コミ・招待動線）で低く保つ

### 4.3 事業マイルストーン

| 段階 | 状態 | 主要指標 |
|---|---|---|
| 短期 | MVP 公開・家族内/知人テスト | 週次アクティブ家族数（WAF）、招待成立率 |
| 中期 | 無料獲得 → 480円初期課金 → SNS認知 | 無料→有料転換率、30日継続率 |
| 長期 | 子育て家庭向けスーパーアプリ化 | LTV/CAC、有料家族基盤 → 事業売却/資金調達/ユニコーン化 |

### 4.4 北極星指標（North Star Metric）

- **WAF: Weekly Active Families（週次アクティブ家族数）**
- 補助指標: 1家族あたり週次操作数 ／ 招待成立率 ／ 30日継続率 ／ トライアル開始率 ／ 有料転換率 ／ 解約率

## 5. プロダクト戦略

### 5.1 フェーズ戦略（正本: `docs/product-roadmap.md`）

- **Phase 1（MVP）**: ログイン/ホーム/予定/タスク/ボード/Hoku基本/プレミアム基礎/データ保存 — 公開品質
- **Phase 2（公開直後）**: 家計/体調/準備/通知/招待/画像/Hoku強化/480円課金
- **Phase 3（拡張）**: クラウド同期の深化・上位プラン・家族レポート・AI整理
- **Phase 4（スーパーアプリ）**: Hoku の家族 AI アシスタント化・統合プラットフォーム

※ 2026-07 現在、実装は Phase 2〜3 相当まで到達済み（Supabase 同期・招待リンク・Web Push・Stripe 決済導線・OCR 取込・Hoku エージェントを含む）。詳細は `02-requirements.md` の実装状態列を参照。

### 5.2 機能採否のフィルタ（ユニコーン視点チェックリスト）

新機能は以下を自問し、**YES が過半に満たなければ B/C に格下げまたは見送り**（CLAUDE.md §10.3）:

- 家族の課題を本当に解決するか／毎日使いたくなるか
- 無料→有料への自然な転換動線になるか／480円の価値を感じられるか
- 競合に真似されにくい体験か／家族単位で継続される仕組みか
- 世界観が一貫しているか／事業売却時にプロダクト資産として説明できるか

### 5.3 やらないことリスト（スコープ防衛）

- 家族外への SNS 発信機能
- 過度なゲーミフィケーション・子どもっぽい演出
- MVP 価値に寄与しない大量機能の同時投入
- 広告モデル（家族の信頼と両立しない）

## 6. グロース戦略（要点）

- **招待がグロースエンジン**: 招待リンク（`?join=FAMI-...`）を開いてログインするだけで家族参加が完了する摩擦ゼロ設計
- 「3児パパが作る家族アプリ」としての SNS・ショート動画発信（当事者コンテンツ）
- TestFlight / 知人家族からの口コミ → オーガニック獲得
- プレスキット（`docs/press/`）を活用した露出
- 計測: 招待成立率・WAF・継続率をリリース後に整備（詳細は `familink-growth-lead` Skill）

## 7. リスクと対応方針

| リスク | 影響 | 対応 |
|---|---|---|
| 大手（TimeTree 等）の機能追随 | 差別化低下 | 統合体験と Hoku の文脈理解で先行し続ける |
| プライバシー事故 | ブランド毀損・致命的 | RLS による家族分離・秘密鍵非搭載・XSS対策を設計原則に（`07-security.md`） |
| LocalStorage 消失 | データ喪失 → 信頼喪失 | クラウド同期を正とする移行・端末保管の案内・保存失敗の可視化 |
| ストア審査（IAP 要件） | ネイティブ配布時に Stripe 不可 | Web/PWA は Stripe、ネイティブ化時は StoreKit/Play Billing を別途実装（`10-monetization.md`） |
| 単一開発者の継続性 | 開発停滞 | 本ドキュメント体系＋QA 自動化＋Skills により誰でも再開可能な状態を維持 |
| AI コスト・品質 | 収益圧迫・体験低下 | Hoku はローカル応答を基本とし、AI 呼び出しは利用制限つきで段階提供 |

## 8. ブランドと世界観（要点）

正本は `08-design-system.md`。事業判断に関わる要点のみ:

- **トーン**: 温かく・安心感があり・押し付けない。子どもっぽくしすぎない上質さ
- **ビジュアル**: 落ち着いた配色・十分な余白・ラインアイコン（SVG stroke）統一・装飾絵文字禁止
- **Hoku**: マスコットではなく「家族を支えるガイド役」。過度なアニメ風にしない
- **コピー**: 簡潔でやさしい日本語（です・ます調）。煽らない・責めない

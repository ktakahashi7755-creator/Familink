# セキュリティ・認証メモ（Wave 66）

Familink に認証・クラウド同期を導入する際の、セキュリティ上の必須事項。

---

## 1. API Secret をフロントに置かない

- Familink は単一 HTML / GitHub Pages 配信 → **フロントコードは全公開される**
- Supabase Service Role Key、管理者キー、Client Secret は**絶対にフロントへ書かない**
- これらは漏洩すると全ユーザーデータへの管理者アクセスを許す
- フロントで使ってよいのは Supabase の **anon key のみ**（公開前提のキー）

## 2. GitHub Pages 公開時の注意

- HTML / JS / CSS はすべて閲覧可能
- コメント・変数名・URL もすべて見える
- ハードコードした秘密情報は `git log` からも復元される
- 秘密情報は環境変数 / バックエンド / Supabase ダッシュボード側で管理

## 3. Supabase anon key と RLS の考え方

- anon key は「誰でも持てる鍵」。これ単体ではデータを守らない
- **Row Level Security（RLS）が実質的なアクセス制御**
- 全テーブルで RLS を有効化し、ポリシーを必ず書く
- RLS なしのテーブルは anon key で全件読み書き可能になる（重大事故）
- ポリシー例：
  ```sql
  create policy "family members only"
  on events for all
  using (
    family_id in (
      select family_id from family_members
      where profile_id = auth.uid()
    )
  );
  ```

## 4. 家族データのアクセス制御

- データは family_id 単位で分離
- 自分が所属していない family_id のデータは読めない・書けない
- family_members テーブルで「誰がどの家族に属するか」を一元管理
- 役割（owner / parent / member / child）で操作権限を段階化
- 退会・家族離脱時は family_members から行削除 → 即アクセス不可に

## 5. 写真・書類 Storage の注意

- Storage バケットにも RLS 相当のポリシーを設定
- パスに family_id を含め、ポリシーで所属チェック
- 公開バケットにしない（署名付き URL でアクセス）
- アップロードサイズ・拡張子を制限
- 書類は個人情報を含むため、保管期間・削除フローを明示

## 6. ログアウト時にデータを消さない理由

- ログアウトは「ログイン状態の解除」であり「データ削除」ではない
- 家族の予定・体調・家計は、再ログインや別端末同期で使う重要資産
- 誤ってログアウトしてもデータが消えないことが、信頼性の最低ライン
- データ削除は「データ初期化」という明示的に別の危険操作として提供

## 7. データ初期化時の確認設計

- ログアウトとは UI / 関数を完全分離
- 二段階確認：
  1. 危険性を明記したモーダル表示
  2. 「削除」という文字をユーザーが入力（一致時のみボタン有効化）
- 実行後も元に戻せないことを事前に明記
- 確認なしの初期化は禁止

## 8. 招待コードのセキュリティ

- 推測されにくい英数字（8〜10 桁以上、辞書語を避ける）
- 有効期限を設定（例：7 日）
- 使用済み / 期限切れは無効化
- ブルートフォース対策（試行回数制限）はバックエンド側で

## 9. 認証情報の扱い

- パスワードは Supabase Auth 側でハッシュ化保管（自前で保存しない）
- セッショントークンは Supabase SDK の管理に委ねる
- LocalStorage に生のパスワードを保存しない
- OAuth は PKCE フローを使う（モバイル）

## 10. やってはいけないこと（禁止リスト）

- Service Role Key をフロントに置く
- RLS なしでテーブルを公開する
- ログアウトで家族データを削除する
- 確認なしでデータ初期化する
- 未実装の認証を「実装済み」に見せる
- API Secret を git にコミットする
- `.claude/settings.local.json` をコミットする

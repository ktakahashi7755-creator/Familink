# Familink Priority 3 設計案（Wave 14）

**作成日：** 2026-05-02
**位置付け：** 既存構造への影響が大きい変更を「実装はせず、安全に進めるための設計案」としてまとめたもの。
**判断基準：** LocalStorage 構造変更 / 単一 HTML 運用への負荷 / iPhone 実機検証の必要度。

---

## 1. カレンダー繰り返し予定（recurring events）

### 1.1 現状
- `S.events = [{id, title, date(YYYY-MM-DD), time, color, member, note}, ...]`
- 1 イベント = 1 日の単発のみ。`date` が string 1 つ。

### 1.2 ユーザー要件
- 毎日 / 毎週 / 毎月 / 平日 / 曜日指定 の繰り返し
- 例：毎週月曜 体操教室、毎週土曜 プール、毎月25日 支払い、平日 朝の準備、毎週金曜 上履き持ち帰り

### 1.3 設計選択肢

#### A. 仮想展開方式（推奨：MVP として安全）
- イベントオブジェクトに `repeat` フィールドを追加：
  ```js
  { id, title, date, time, color, member, note,
    repeat: {
      type: 'daily' | 'weekly' | 'monthly' | 'weekdays' | 'custom',
      days: [0..6],        // weekly/custom 用（0=日曜）
      monthDay: 1..31,     // monthly 用
      until: 'YYYY-MM-DD'  // 終了日（任意）
    }
  }
  ```
- LocalStorage 構造は **追加のみ**（既存の `events` 配列は破壊しない）
- 表示時に `expandRecurringEvents(events, fromDate, toDate)` で仮想展開
- 既存予定（`repeat` なし）は従来通り単発として扱う
- **影響**：`renderCalendar` / `getEventsForDate` の各所で展開ロジック呼び出し追加

#### B. 親子レコード方式
- 繰り返し定義を別配列 `S.eventRecurrences` に分離
- 各実イベントは `{recurrenceId, ...}` で親参照
- 完全な編集可能性（個別の例外）が得られるが、構造変更が大きい
- 段階導入には不向き

### 1.4 推奨実装ステップ
1. **Step 1：UI のみ追加**
   - 予定追加モーダルに「繰り返し」ドロップダウン（なし/毎日/毎週/毎月/平日）
   - 入力は `repeat` に保存するだけ、表示は単発のまま
   - 既存予定との互換性のみ検証

2. **Step 2：仮想展開を表示に反映**
   - カレンダー月表示で `repeat` を展開して描画
   - 選択日のリストでも展開
   - 個別イベントの完了 / 削除はまだ無効化

3. **Step 3：例外管理**
   - 1 回スキップ（その日だけ削除）
   - 「以降すべて削除」「この日だけ変更」

### 1.5 実装コスト見積
- Step 1：1 セッション（4-8 時間）
- Step 2：1-2 セッション
- Step 3：2-3 セッション

### 1.6 リスク
- iPhone Safari の Date 型処理での月またぎバグ → JST 固定で `YYYY-MM-DD` 文字列演算に統一
- 大量繰り返し（毎日 × 1 年）の描画パフォーマンス → 表示範囲を limit
- 既存 LS データ（`repeat` なし）の forward-compat 検証必須

## 2. 曜日ごとのルーティン準備（weekly routine prep）

### 2.1 現状
- `S.prep = [{id, text, cat, done, date}, ...]`
- 単発の項目のみ。ルーティン概念なし。

### 2.2 ユーザー要件
- 月曜：体操着、上履き、連絡帳
- 火曜：プールバッグ、水筒
- 金曜：上履き持ち帰り、給食袋
- 毎週繰り返す準備をテンプレートとして登録

### 2.3 設計選択肢

#### A. ルーティンテンプレート方式（推奨）
- 新規 LS フィールド追加（破壊なし）：
  ```js
  S.prepRoutines = [{
    id, dayOfWeek: 0..6, text, cat, child, active: true
  }];
  ```
- 毎日初回起動時に「今日の曜日のルーティン」を `S.prep` へ自動注入
  - 重複防止：`originRoutineId + date` で既存チェック
- ユーザーが完了 / 削除できる（その日の prep アイテムとして独立）
- ルーティン自体の編集は別画面 `s-prep-routines`

#### B. 動的計算方式（ストレージ最小）
- `S.prepRoutines` のみ保持
- 各日表示時に「ルーティン + 単発」を on-the-fly でマージ
- 完了状態は別の `S.prepRoutineCompletions = {[routineId]: {[date]: bool}}` に保存
- データは軽いが UI 実装が複雑化

### 2.4 推奨実装ステップ
1. **Step 1：UI 設計のみ**
   - 設定 or 準備リスト画面に「ルーティン管理」エントリ
   - 曜日 × 持ち物のマトリクス表示
2. **Step 2：自動注入ロジック**
   - 起動時 / 日付変更時に該当曜日のルーティンを `S.prep` に追加
   - 注入された項目には `originRoutine` フラグ付与
3. **Step 3：時間割連携（後述 §3）**

### 2.5 実装コスト見積
- Step 1：4-6 時間
- Step 2：6-10 時間
- Step 3：別計画

## 3. 時間割との本格連携（school timetable）

### 3.1 現状
- 時間割の概念なし。
- 子ども別の準備リストもなし。

### 3.2 ユーザー要件
- 月曜：国語、算数、体育 → 体操着が必要
- 水曜：図工 → 図工バッグが必要
- 子どもごとに時間割を登録、それに応じた準備を自動提示

### 3.3 設計選択肢
```js
S.timetables = {
  [childId]: {
    [dayOfWeek 0..6]: {
      subjects: ['国語', '算数', '体育'],
      defaultPrep: ['体操着', '上履き']
    }
  }
};
S.subjectPrepMap = {
  '体育': ['体操着', '体育館シューズ'],
  '図工': ['図工バッグ', 'スモック'],
  '書道': ['書道セット'],
  // ...
};
```

### 3.4 推奨実装ステップ
1. **Step 1：時間割登録 UI**（子ども別 / 曜日別 / 教科リスト）
2. **Step 2：教科 → 持ち物のデフォルトマップ提供**
3. **Step 3：曜日切替で「明日の時間割 + 持ち物」を表示**
4. **Step 4：ルーティン準備（§2）と統合**

### 3.5 実装コスト見積
- Step 1：8-12 時間
- Step 2-4：合計 2-4 セッション

### 3.6 結論
- **MVP v0.1 では実装不要**。家族実利用での需要検証後に v0.2 / v0.3 で着手。
- 着手前に「現実の小学校・幼稚園の時間割」を 5-10 家庭からヒアリング推奨。

## 4. カンバン機能の撤廃 / 非表示

### 4.1 現状
- タスク画面に「リスト / カンバン」切り替えあり
- カンバンは 4 列（todo / doing / hold / done）+ 横スクロール
- スマホで横スクロールが直感的でない、一部しか見えない

### 4.2 ユーザー判断
- カンバンを撤廃 → リストに統一して OK

### 4.3 安全な撤廃ステップ

#### Step 1：UI からの非表示（最小・安全）
- タスク画面のヘッダーから「カンバン」切り替えボタンを削除
- `_tkView` を `'list'` に固定
- カンバン関連 CSS / 関数はコードに残す（表示されないだけ）
- LocalStorage `S.kanbanCols` は残置（既存ユーザー保護）
- **影響範囲：HTML の 1-2 行削除のみ**

#### Step 2：完全撤廃
- `tkKanbanCard()` / `getKanbanCols()` / `KANBAN_COL_DEF` / 関連 CSS を削除
- `S.kanbanCols` は PERSIST から外す（次回保存時に消える）
- カンバン関連の draggable ロジックも削除
- コミット 1 回で完結（影響範囲限定）

### 4.4 推奨：Step 1 を Wave 15 で即実施
- リスクほぼゼロ
- ユーザー混乱の解消が即座に得られる
- 完全撤廃（Step 2）は様子見でも OK

## 5. 子ども / 体調管理ボードの拡張

### 5.1 現状
- `s-health` 画面：子どもタブ + 体温・症状・薬・メモ記録
- `s-cdetail` 画面：子ども詳細（プロフィールのみ）
- カスタムボードで「体調管理」を作れるが、既存の `s-health` とデータが分離

### 5.2 ユーザー要件
- 子どもごとの状態 / 体調を見える化できるボード
- 体調 + 習い事 + 学校での出来事 + 準備物を一元管理
- プロフェッショナルな見た目

### 5.3 設計選択肢

#### A. 既存 `s-health` の強化（推奨）
- 子どもタブ単位で「体調 + 出来事 + 準備 + 習い事ログ」を集約
- 新規 LS フィールド：`S.childLogs = [{id, childId, type: 'health'|'event'|'prep'|'lesson', title, body, date, ...}]`
- 既存の `S.health` は読み込み時に `childLogs.health` として併合
- フィルター UI で type 切り替え

#### B. カスタムボードベース
- 子どもごとに「{childName}メモ」ボードを自動生成（type: 'share'）
- カテゴリで体調 / 出来事 / 準備 / 習い事を区分
- 既存の `S.health` とは独立（重複の懸念あり）

### 5.4 推奨実装ステップ
1. **Step 1：UI スケッチ作成**
2. **Step 2：`s-health` を「体調」から「子ども別ログ」へ画面名変更**
3. **Step 3：`childLogs` 追加 + UI 統合**
4. **Step 4：既存 `S.health` データのマイグレーション**

### 5.5 実装コスト見積
- 8-16 時間（中規模）

### 5.6 結論
- **MVP v0.1 では Step 1 のみ**（設計）
- v0.2 で実装着手。Hoku の「体調記録」誘導とも連動して再設計。

## 6. 通知 / リマインド連携

### 6.1 現状
- `s-notif` 画面はあるが、過去通知の表示のみ
- ローカル通知（プッシュ）は未実装

### 6.2 検討
- Web Push は HTTPS + Service Worker 必須 → GitHub Pages では実装可能だが iPhone Safari の Web Push 対応は限定的
- 妥協案：当日朝の起動時に「今日の予定 + 準備」を Hoku が自動表示
- v0.2 以降で WKWebView ラッパー化したらネイティブ通知へ

### 6.3 結論
- **MVP v0.1 では実装不要**
- 設計：`docs/iap-integration-plan.md` / `docs/roadmap-to-mvp-v1.md` 参照

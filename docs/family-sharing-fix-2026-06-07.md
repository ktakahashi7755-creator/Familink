# 家族共有が動かない件：診断結果と「いますぐやること」（2026-06-07）

> 結論：**アプリ側の実装は完成しています。動かない原因はほぼ Supabase（DB）側の設定です。**
> あなたが下の「STEP 1〜3」を実行すれば家族共有が動くはずです（所要 約5分）。
> 実行後は、アプリの隠し診断 **`#qa-debug`→「家族共有セルフテスト」** で合否を即確認できます。

---

## 0. 今回の調査でわかった事実（実際の Supabase を叩いて確認）

| 項目 | 結果 | 意味 |
|---|---|---|
| テーブル `fl_family_data` | **存在する** | スキーマは作成済み |
| 関数 `fl_my_family_ids()` | **存在する** | 家族横断読み取りの補助関数は作成済み |
| RLS（行レベルセキュリティ）| **有効**（匿名の書き込みは正しく拒否） | 保護は効いている |
| 家族横断の読み取り `family_read` | **未確認**（要ログイン検証） | ★これが未適用だと家族のデータが読めない |
| Realtime publication | **おそらく未設定** | ★未設定だと「即時」反映されない（20秒ごとの取得は動く）|
| メール確認（Confirm email）| **ON（自動確認OFF）** | ★家族が登録しても確認メール未処理だとログインできず同期されない |

→ 「家族共有できない」の最有力原因は **(A) 家族横断読み取りの SQL が未適用／旧版** か **(B) 家族メンバーがメール未確認でログインできていない**。多くの場合この2つです。

---

## 1. なぜ起きるか（仕組み）

- Familink は各端末が自分のデータを Supabase に保存し、**同じ家族コード(`family_id`)を持つ全員の行をまとめて取得**して画面に反映します。
- そのためには DB 側で「**同じ family_id の家族の行を読んでよい**」という許可（RLS の `family_read` ポリシー）が必要です。これが無いと「自分の行」しか読めず、**別アカウント＝家族間の共有は成立しません**（同一アカウントの複数端末同期だけ動く）。
- さらに「**即時**反映（リアルタイム）」には、テーブルを Supabase の Realtime に登録する1行が必要です。未登録でも、アプリは**20秒ごとに自動取得**するので共有自体は動きます（少し遅れるだけ）。

---

## 2. いますぐやること（オーナー作業・約5分）

### STEP 1 ── 共有用 SQL を実行（最重要）
1. Supabase ダッシュボード → 対象プロジェクト → **SQL Editor**
2. リポジトリの **`docs/supabase-setup-sql.sql` を全文コピー**して貼り付け → **Run**
   - テーブル・関数・RLS(`family_read`)・Realtime をまとめて正しい状態にします（冪等：何度実行してもOK）。
   - `already member of publication` 等のエラーは出ない作りですが、出ても無害です。

### STEP 2 ── メール確認をOFF（家族の登録を簡単に）
- Authentication → **Sign In / Providers → Email** → **「Confirm email」を OFF**
  - これで家族は登録後すぐログインできます（確認メール待ち・迷惑メール問題を回避）。
- ON のままにしたい場合は、家族には登録後に届く**「6桁コード(OTP)」**を使ってもらうのが確実（無料SMTPは1時間2通制限あり）。

### STEP 3 ── 動作確認（2アカウント）
1. 端末A：ログイン → 予定/やることを数件追加 → 設定 →「家族を招待する」でコード(`FAMI-XXXX-…`)を発行。
2. 端末B：**別アカウント**でログイン →「招待コードで参加」にAのコードを入力。
3. 端末B に A の予定が出れば**共有OK**。端末Bで1件追加 → 数秒〜20秒でAに出れば**リアルタイムOK**。

---

## 3. 今回アプリ側でやったこと

- **`#qa-debug`→「家族共有セルフテスト」ボタンを新設**（オーナー診断用）。実アカウントで押すと、
  1. 自分のデータ送信、2. 家族データ取得（**他メンバーの行が読めているか＝RLS判定**）、
  3. **Realtime 配信の実測**（publication 有無を判定）、4. **メール確認設定の判定**、
  を順に実行し、**どのレイヤーで失敗しているか**と対処を日本語表示します。
  → STEP 1/2 実行後にこれを押せば「直ったか」が一目でわかります。
- **`docs/supabase-setup-sql.sql` を新設**（貼り付け1回で完了する冪等な最終SQL）。
- 既存の詳細記録 **`docs/family-sync-fix.md`** に、今回の診断（メール確認ON・Realtime publication）を上乗せ。

> アプリの同期ロジック（family_id で家族全員分を取得しマージ／per-item last-write-wins／
> Realtime 自己回復／20秒ポーリング保険／復帰時フェッチ）は既に実装済みで、変更していません。

## 4. それでも共有できない場合の切り分け（セルフテストの読み方）

| セルフテストの表示 | 原因 | 対処 |
|---|---|---|
| ②が「自分の行のみ」（家族は参加済みなのに）| RLS `family_read` 未適用 | **STEP 1 の SQL を再実行** |
| ②でメンバーが増えない | 家族がログインできていない／別の家族コード | STEP 2（メール確認OFF）＋同じコードで参加 |
| ③ Realtime「イベント未受信」| publication 未設定 | STEP 1 の SQL（publication行）を実行。未設定でも20秒で共有は動く |
| ①送信が失敗 | 通信／ログイン切れ | 再ログイン・通信確認 |
| ④メール確認 ON 警告 | 家族が未確認で入れない | STEP 2 で OFF、または OTP コード方式 |
